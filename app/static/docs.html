并行处理

并行分两层，可在设置页调整（即时生效，持久化到 dirs.settings_file，默认 /data/settings.json）：

  • concurrency（并行任务数，默认 1）：同时转码几个文件。增大后多个任务同时进行，会显著提高 CPU/内存占用。
  • av1an_workers（任务内切片并行，默认 0）：每个任务内部 av1an 用多少线程并行编码切片；0 = 自动（av1an 按 CPU 核数分配）。只对 engine=av1an 的任务生效，每个任务开始时读一次；optimizer 引擎不看它，它的并行由 probe_workers / encode_workers 决定（0 都是按容器的 cgroup 预算自动算）。

各取值对资源占用的影响：concurrency × av1an_workers 约等于 av1an 引擎峰值同时运行的编码进程数。减小并发数即时生效：已排队的任务不受影响，当前任务完成后对应的 worker 会自动退出。

已知问题：同一次运行里减小过并发数、再调大时，新开的 worker 会立刻退出，设置页的「运行中的 worker」停在减小后的数目，日志却照样写 Grew worker pool to N。绕过办法：先按「运行中的 worker」当前的数目保存一次，再保存想要的值；或者等队列空了重启（新值已经存盘）。

工作流程

默认不会自动入队任何文件（watcher.enabled: false）：只有通过首页表单 / API POST /api/jobs / CLI（process、scan）手动指定的文件或目录才会被转码。如需恢复自动监视，在 config.yaml 中设置 watcher.enabled: true。

提交的文件会分析（Dolby Vision P5 → HDR10，P7/P8 编码基底层、按基底层的 HDR10/HLG/SDR 标记（RPU 默认另存为 .rpu，成品本身不带 DV），HDR10/HLG/SDR 直接编码），随后按预设的码率/质量参数编码输出为 AV1（SVT-AV1）。

  • 已是 AV1 的源默认跳过（skip_existing_av1）。
  • 成功后源文件默认保留在原位置。可选：在设置页开启「转码成功后删除源文件」（需要二次确认，危险操作）。

输出行为

默认（dirs.output/dirs.rpu 为 null）转码输出到源文件所在目录下的 av1/ 子目录：

S1/
├── Show.S01E01.Title.Bluray-2160p.Remux.h265.DTS-HD.MA.DV.HDR10.mkv    # 源文件
└── av1/
    ├── Show.S01E01.Title.Bluray-2160p.Remux.AV1.DTS-HD.MA.HDR10.mkv    # 转码输出
    └── rpu/
        └── Show.S01E01.Title.Bluray-2160p.Remux.AV1.DTS-HD.MA.HDR10.rpu    # 抽取的 Dolby Vision RPU（仅 DV 源且 save_rpu=true）

输出沿用源文件名，只改 Sonarr/Radarr 重命名时会变的两处：编码标记（h264/h265/x264/x265/AVC/HEVC/H.264/H.265/MPEG2/VC1/VP9/XviD/DivX）换成 AV1；动态范围里成品带不走的 DV 和 HDR10+ 按成品实际改写（DV.HDR10、HDR10+ → HDR10，DV.HLG → HLG，DV.SDR 删去）。动态范围只在分辨率（如 2160p）之后查找，片名里的词不会被改。文件名里没有编码标记时（如 Big Buck Bunny.mkv）输出为旧式的 Big Buck Bunny.av1.mkv。RPU 与成品同名、扩展名 .rpu——.bin 在 Sonarr/Radarr/Plex 里是视频扩展名，会被当成一集。

若在 config.yaml 中配置了固定的 dirs.output/dirs.rpu，则所有输出集中到这些目录。监视器（watcher）会排除 av1/work/rpu 目录，避免把转码输出再次入队。

预设与编码参数

预设可在设置页添加/编辑/删除并持久化（存于 dirs.presets_file，默认 /data/presets.json）。自定义预设可覆盖内置同名预设，内置预设删除后自动恢复 config.yaml 中的定义。

codec

默认 svt-av1

编码器，唯一合法值是 svt-av1：写别的值，保存预设会返回 422，写进 config.yaml 则启动时校验失败；作为自定义参数传进来不报错，也不起作用。两个引擎其实都不读它，编码器是写死的（av1an 引擎传 --encoder svt-av1，optimizer 引擎的正式编码用 ffmpeg 的 libsvtav1），所以设置页的预设编辑器里没有这一项。

自定义参数（临时覆盖，不写回预设）

首页表单的“自定义参数”框按逗号/分号分隔多个 key=value；CLI 用 --custom key=value，一次一个、可重复。两边都只在第一个 = 处切开，所以值里还能带 =，如 probe_video_params=preset=10。值会覆盖所选预设的同名字段：

crf=24,preset=3,target_quality=75-85,film_grain_denoise=true

CLI 会转类型：数字字段转 int（crf/preset/film_grain/luminance_qp_bias/passes/keyint/extra_split_sec/min_scene_len/tune/probes/probing_rate/vmaf_threads），布尔字段接受 true/false/1/0（film_grain_denoise），其余按字符串（target_quality、additional_video_params、pixel_format）。首页表单目前不转：每个值都按输入的字符串提交，服务端也不再转换，所以要跟数字比大小的字段从首页填会让作业失败，已知的有 passes（av1an 引擎）、probes 和 probing_rate（optimizer 引擎）；这几项请写进预设，或用 CLI / API（overrides 里直接给数字）。

不认识的键和空值服务端直接忽略（首页会提示不认识的键）。覆盖值随作业存进任务库，重试时照样生效，但不会写回预设。预设选 custom 时以默认预设（transcode.default_preset，默认 balanced）当前的值为基准，只改自定义参数里写到的项。

Shot-based 优化器引擎（engine=optimizer）

Netflix 风格的逐镜头（shot-based）编码。av1an 的 --target-quality 是串行探测：先完整探测完一个 chunk 再探测下一个。optimizer 引擎改为所有镜头并行探测，并用插值获得比 av1an 4 次二分更精细的每镜头 CRF：

  1. 分镜：默认用 ffmpeg 的 scdet 滤镜单趟扫描源，不落任何中间文件（scenedetect_engine: scdet）。实测对三个 4K 源，切点与旧的 PySceneDetect 路径一处完全一致、另两处各多一个；整个阶段从 44.7s / 255s CPU 降到 12.2s / 8s。scenedetect_engine: pyscenedetect 可切回旧路径（写一份降采样副本再用 OpenCV 逐帧读）。切出来的镜头再按 min_shot_frames、max_shots 合并。
  2. 并行探测：所有镜头按内存和 CPU 预算尽量多地同时探测（probe_workers 只是可选的硬上限，见并发与内存）。每个镜头先探 probe_crfs 网格的两端和中间点，再在夹住目标的区间里二分，区间窄到 probe_bracket_width 就停（设 0 则整张网格全探）。每个探测点按源分辨率、与正式编码相同的像素格式和编码参数（仅 preset 更快）编码，再按 target_metric 打分（VMAF、SSIMULACRA2 或 XPSNR）。用 VMAF 时，源宽低于 vmaf_4k_min_width（默认 2560）的，送进 libvmaf 前两路统一缩到 vmaf_width（默认 1920，只缩不放、保持比例），因为 vmaf_v0.6.1 是按 1080p 训练的；达到这个宽度的改用 vmaf_model_4k 按原生分辨率打分。镜头过长时按 probe_max_frames 取中间一段连续帧。probe_encoder 选 qsv 或 qsv+svt 时显卡也参与探测。
  3. 选 CRF：对每个镜头在 (CRF, 分数) 曲线上插值，取命中 target_quality 下限的 CRF（区间超出探测范围时钳制到边界）。然后加上 probe_crf_offset，按 min_crf / max_crf 钳制，再用 max_crf_delta 平滑相邻镜头。
  4. 并行编码：所有镜头按各自 CRF 并行正式编码，最后拼接并重新复用源音频/字幕。
  5. 校验：按 verify_shots 从成品里抽几个镜头重新打分，对账探测预测和实际交付（见成品校验）。

启用方式：预设（设置页或 CLI --custom engine=optimizer）里设 engine=optimizer，并配合 target_quality（必填，如 75 或 75-85）。自定义参数同样适用：--custom engine=optimizer --custom target_quality=80 --custom target_metric=ssimulacra2。

预设里的几项会盖过下面的全局值：probing_rate、vmaf_threads 非 0 时分别盖过同名项，probe_res 非空时盖过 probe_scale；probe_video_params 里 optimizer 只认 preset=N（copy = 与正式编码同一个 preset），用来盖过 probe_preset，其余参数不看，探测总是沿用正式编码的参数；probes 非 0 且少于网格点数时，只取 probe_crfs 里均匀分布、保留两端的 probes 个点。probing_vmaf_features 没有对应的全局值：av1an 语法（如 default motionless）optimizer 会忽略并打一次告警；含 = 或 | 的合法 ffmpeg libvmaf 配置会原样透传给 feature=。填了任何值（包括被忽略的 av1an 语法），这个作业都不走零拷贝打分。预设里的 min_scene_len 只给 av1an 用。

分镜 先把源切成镜头，后面所有探测和编码都按镜头进行

scenedetect_engine

默认 scdet

分镜用哪个检测器。scdet = ffmpeg 的场景变化滤镜，单趟读源、不落盘，门限看 scdet_threshold；pyscenedetect = 旧路径，先写一份降采样副本再用 OpenCV 逐帧读，门限看 scenedetect_threshold。两条路都先按 scenedetect_scale 缩小、都用 min_scene_len，实测对比见本章第 1 步。只有 scdet 那一趟会记下每帧的时间戳：恒定帧率检查和时间线空洞的处理都靠它，pyscenedetect 路径两样都没有。留着旧路径是为了能在真实片源上对照。

去设置页 ›

scdet_threshold

默认 2.0

仅 scenedetect_engine=scdet 时生效。一帧的 scdet 分数（0-100）达到它才算切点，越低越敏感。ffmpeg 自己的默认 10 对电影电视太高：在一段 4K 样片上只找到 21 个切点中的 1 个。2.0 与旧检测器的结果很接近，0.8-1.5 还会抓到较软的转场；低于约 0.5 多出来的多半是镜头运动或光线变化，而且会挤掉正确的切点。

去设置页 ›

scenedetect_threshold

默认 27.0

仅 scenedetect_engine=pyscenedetect 时生效。ContentDetector 灵敏度；越高分镜越少、片段越长。

去设置页 ›

scenedetect_scale

默认 -2:540

分镜前先把画面缩到这个尺寸（ffmpeg scale 的写法），只为提速；空 = 原生分辨率。scdet 下实测 540p 和原生选出的切点一样。pyscenedetect 下它决定那份降采样副本的尺寸，留空就让 OpenCV 直接逐帧解源，4K HEVC 会慢到不可用。写成 W:H（一边可用 -1/-2 按比例算）时，分镜这一趟的解码和缩放才能交给显卡（见 scenedetect_hwaccel）。

min_scene_len（优化器）

默认 24

最小镜头长度（帧），更短的会合并。它管的是切点：scdet 下离上一个切点不足这么多帧的候选切点直接不切，取先到的、不取最强的；pyscenedetect 下原样交给 ContentDetector。切完之后再合并短镜头用 min_shot_frames。预设里的同名参数只给 av1an 用。

去设置页 › ↔ 预设里的同名参数

min_shot_frames

默认 0

短于这么多帧的镜头并入相邻镜头（每次挑最短的，并进两边较短的那个邻居），0 = 不合并。默认关：本引擎只在真实切点处切，那里的关键帧编码器本来就要花，合并省不出体积；它省的是探测次数，代价是逐镜头 CRF 更粗。探测是瓶颈时再开，96 帧及以上实测会多花体积。

max_shots

默认 3000

镜头数量上限；超过时合并最短的相邻镜头。

去设置页 ›

探测 每个镜头在源分辨率下用快速 preset 编几个 CRF，量出它自己的质量曲线

probe_crfs

默认 [20,26,32,38,44]

每个镜头采样的 CRF 网格。默认的自适应探测（probe_bracket_width 大于 0）从网格两端和中间点起步，再在夹住目标的区间里二分，所以网格决定去哪里看，点数就是每个镜头最多探几次。probe_bracket_width 为 0 时整张网格全探，越密越准、探测越多：探测按源分辨率跑，每多一个点就多一遍全片探测。能交付的范围另由 min_crf / max_crf 管。

去设置页 ›

probe_encoder 进阶

默认 svt

探测编码用哪个编码器。svt = 原有路径。qsv = 在显卡上探测，再用逐作业标定把质量索引映射回 SVT 的 CRF，映射出的 CRF 直接交付；标定不可靠时整个作业退回 SVT，质量索引超出锚点范围或两端夹不住目标的镜头逐个退回 SVT。qsv+svt = 同样的显卡工作换一种用法：映射出来的 CRF 只决定 SVT 从哪里开始探，交付的 CRF 仍然来自 SVT 探测，所以映射错了只多花一次探测。两种显卡模式都要容器里有 /dev/dri 渲染节点，没有就按 svt 跑并打一条告警；显卡探测编码现在走 VA-API 的 av1_vaapi，模式名里的 qsv 是沿用下来的叫法，它和 GPU 打分共用一份显存预算（见 GPU）。实测 qsv+svt 的探测阶段比 svt 合计快 27%（三段 4K 杜比视界片段共 912 个镜头），选出的 CRF 与 svt 相差不超过 1 的镜头占 96–100%。

资源占用：探测和正式编码都不是固定大小的 worker 池，而是逐个镜头按预算准入，放得下就启动一个 SVT-AV1 实例；每个实例的内存按镜头（探测窗口）长度和分辨率估算，作业进行中再按实测峰值校正。为防线程爆炸，每个实例的 lp 取剩余 CPU 预算里放得下的最大一档（4、3、2、1），同时在跑的实例 lp 之和不超过可用核数（探测按 probe_cpu_charge 折算），总 lp≈核心数；探测读源时的解码线程数也设成这个 lp。可用核数是本容器的 cgroup CPU 配额与亲和掩码取小，不是机器的核数。内存只决定放不放行：预算是本容器可用内存的 85%（有 cgroup 限额时是限额减去不可回收的占用，否则是 MemAvailable），每次准入前还会再看一眼实时余量、取小的那个；只有什么都没在跑、这个镜头仍装不下时，才为了内存往下降 lp。lp 只决定帧池大小，不改变码流。若仍然吃紧（例如编码被 OOM 杀掉），用 probe_workers / encode_workers 设硬上限。

临时文件在 dirs.work 下，每个作业一个目录，成功或失败后整个删掉，除非开了 keep_temp；keep_probes 只让探测文件在作业进行中不被逐个删掉，作业结束后还要看就得同时开 keep_temp。Dolby Vision P5 和 SSIMULACRA2 按镜头暂存的参考分片优先放在 transcode.dovi.p5_cache_dir（默认 /dev/shm），放不下才落到作业目录，用完即删。

GPU 与硬件

GPU 在这里只做加速：每一步都有 CPU / 软解的路径，GPU 让其中几步更快、更省 CPU。除 Dolby Vision P5 转换外，用到 GPU 的都在 optimizer 引擎（engine=optimizer）里。开关在设置 → GPU，共八项：七项是优化器参数（transcode.optimizer），每个作业开工时读一次，所以保存不影响正在跑的作业；vulkan_device 属于 transcode.dovi，每次 P5 转换时现读。

  1. 分镜解码（scenedetect_hwaccel）：分镜那一趟用 QSV 解码，并在显卡上缩到 scenedetect_scale 的尺寸，再下载回内存做检测。QSV 打不开、卡解不了这种编码（B580 解 AV1 会正常退出却一帧不出）、或 scenedetect_scale 为空或不是纯 W:H 时，自动改用软解。
  2. VMAF 打分（vmaf_sycl_device、vmaf_sycl_min_width）：探测打分和成品校验的 libvmaf 改走它的 SYCL 后端（滤镜参数 sycl_device=N），需要镜像里带 SYCL 的 libvmaf 和一块 Level Zero 设备（Intel Arc）。只对 target_metric=vmaf 且源宽不小于 vmaf_sycl_min_width 的作业生效；SSIMULACRA2 和 XPSNR 始终在 CPU 上算。作业第一次打分前先自检：同一对测试画面在 GPU 和 CPU 上各打一次，后端必须自报 SYCL、两边相差不超过 1e-3，不过就整个作业在 CPU 上打分，不再重试。之后单次 GPU 打分出错或超时（60 秒加每帧 1 秒；探测编码也在显卡上跑时翻倍），这个窗口改在 CPU 上重打；连续 3 次，本作业改用 CPU，300 秒后再自检一次，过了回到 GPU，再不过就一直用 CPU。
  3. 显存与并发（vmaf_sycl_workers、gpu_vram_budget_mb）：显卡只有一块显存，GPU 打分、零拷贝打分和显卡上的探测编码从同一份预算里放行：同时进行的不超过 vmaf_sycl_workers 个，新操作的显存估算要放得进 gpu_vram_budget_mb 减去当前占用（占用取估算总和与 DRM fdinfo 实测中较大的那个）。GPU 打分等 120 秒还放不进，就改在 CPU 上打。
  4. 零拷贝打分（vmaf_zero_copy）：探测打分时源窗口和探测文件两路都在 VA-API 上解码，帧直接交给 libvmaf 的 SYCL 后端，不回传内存。前提：SYCL 打分已生效；按原生分辨率打分（4K 模型，或源宽不超过 vmaf_width 的 1080p 模型，都不缩放）；没设 probe_scale；没设 probing_vmaf_features（只导入亮度）；源位深不高于探测编码（8-bit 源配 10-bit 探测时，两路都在显卡上用 scale_vaapi 转成 P010，对应常规读取里的 format=yuv420p10le）；镜像里的 libvmaf 带 libva、ffmpeg 带配套补丁。每个作业先预检：定位后的 VA-API 读取要和软解逐帧一致（与 reference_hwaccel 同一个预检），再用一个窗口两种方式各打一次分，libvmaf 必须报告是在显卡上原地导入的、两个分数相差不超过 1e-3，否则整个作业走常规读取。单个窗口失败就用常规读取重打并记住它，连续 8 次失败本作业关掉零拷贝。Dolby Vision P5 作业的参考是逐镜头预先转好的分片，不走零拷贝；成品校验也不走。
  5. 打分参考读取（reference_hwaccel）：探测打分和成品校验里读源片的那一路用 VA-API 解码（第一个 /dev/dri/renderD*），下载回内存后交给打分。用 VA-API 不用 QSV 不是偏好：QSV 是独立的解码器、自己处理时间戳，定位之后在带时间轴空洞的 mkv、DV P5 mp4、8-bit H.264 WEB-DL 上保留的帧和软解不同——像素一致、帧全错；VA-API 只是给 ffmpeg 自带的解码器加速，选帧和软解一样，九种情况九次分数完全一致。auto 时每个作业先在定位后各解 8 帧，软解和硬解逐帧 md5 对比，不一致整个作业软解；某个窗口硬解失败就在 CPU 上重打并记住它，连续 8 次失败本作业改回软解。只放这一路上 GPU：4K 帧从显存回传约 130 帧/秒封顶，而探测文件和成品的 AV1 用 dav1d 软解更快。
  6. 探测编码（probe_encoder）：设成 qsv 或 qsv+svt 时，显卡的硬件 AV1 编码器也参与探测（VA-API 解码直接进编码器），机制、退回和实测见 probe_encoder。容器里没有 /dev/dri 渲染节点时自动退回 svt 并告警。
  7. Dolby Vision P5 转换（vulkan_device）：P5 的基底层是 ICtCp，要由 libplacebo 应用 RPU 才能变成 HDR10，而 libplacebo 跑在 Vulkan 上（ffmpeg 的 -init_hw_device vulkan）。optimizer 引擎逐镜头转换，av1an 引擎整片转换。没指定设备时让 ffmpeg 挑：容器里有 GPU 就用 GPU，没有就用 Mesa 的 llvmpipe 软件渲染，照样能转，只是在 CPU 上跑。

始终留在 CPU 上的：SVT-AV1 编码（SVT 探测和全部正式编码）、正式编码读源、探测文件和成品的 AV1 解码、SSIMULACRA2 与 XPSNR 打分。GPU 解码值不值，看旁边那个编码有多贵：分镜只有解码，收益最大；正式编码 preset 4 只有 3% 花在解码上，挪到 VA-API 峰值内存反而 +8.7%。

设置页的检测与自检

设置页的 GPU 区不读 sysfs，而是像流水线自己那样通过 ffmpeg 去探：有哪些 /dev/dri/renderD* 渲染节点，libvmaf 编没编进 SYCL 后端，SYCL 设备叫什么（按已保存的 vmaf_sycl_device 序号去问，关闭时问 0 号）、一共几个，ffmpeg 列出哪些 Vulkan 设备，QSV 和 VA-API 能不能打开，以及找不找得到 ffmpeg。数据来自 GET /api/gpu（开放读取，结果缓存 5 分钟）；「重新检测」发的是 GET /api/gpu?refresh=true，跳过缓存重探一次。

「自检打分」发 POST /api/gpu/selfcheck（需 api_key），用的是表单里当前选中的设备，不必先保存，所以可以先试再存。它和优化器开工前的自检是同一个测试：同一对测试画面在该 SYCL 设备和 CPU 上各打一次，后端必须自报 SYCL、两边相差不超过 1e-3 才算通过；不通过，用这个设备的作业会自动退回 CPU 打分。端点的完整列表见 API。

上面这些退回都不让作业失败：作业照常完成，只是更慢、更吃 CPU。整个作业退回 CPU 或软解时，说明原因的那一行只写进程序日志（dirs.logs 下的 av1transcode.log），队列页能看的作业日志里没有。所以「现在的设置会怎么用」按已保存的设置和刚探到的硬件解析出四条路径，会退回的标成琥珀色：

  • VMAF 打分：「设置为设备 N，但现在不可用 → 作业会退回 CPU」。
  • 分镜解码：「auto，但 QSV 不可用 → 软解」。
  • 打分参考解码：「auto，但 VA-API 不可用 → 软解」。
  • P5 转换：「自动，但没有设备」。这一条不是退回：P5 没有 Vulkan 以外的路，建不了 Vulkan 设备时 P5 转换直接失败。

「这台机器有什么」的设备卡上，琥珀点同样是降级但能用：SYCL 后端看得到设备，配置的那个序号却不可用；Vulkan 只有 llvmpipe 这类软件渲染器；QSV 和 VA-API 都打不开。红点是缺了东西：没有渲染节点，libvmaf 没有 SYCL 后端或一个 SYCL 设备都看不到，一个 Vulkan 设备都没有，找不到 ffmpeg。

新增的 srt 轨

  • 哪些轨会有：复用保留下来的 ASS/SSA 轨；语言 tag 是 eng、en、english、en-us、en-gb、eng-us 之一（不分大小写）的 PGS 轨，没有语言 tag 不算英文。判定为空的轨一律不做，即使 drop_empty_subtitles 关着、它被留在了成品里。文件里已经有英文文本字幕，英文 PGS 照样 OCR：SDH 图形轨和普通字幕是两份不同的字幕。
  • 排在哪：源的字幕之后，先 ASS 的，再 OCR 的。
  • 语言与标题：语言照原轨。标题是原轨标题后加 (SRT) 或 (OCR)，如 English SDH (OCR)；原轨没有标题时是 SRT (plain text) 或 OCR (plain text)。
  • 标记：原轨是 default 时，default 移到新的 srt 上，原轨写成非 default——两条都是 default 时播放器取第一条，也就是原轨，是图形轨的话 Plex 照样选它烧进画面。forced 两边都有。hearing_impaired：OCR 出来的 srt 照抄，因为从 SDH 图形轨读出来的文字仍是 SDH，图形轨自己也保留；ASS 旁的 srt 不带，这个标记只留在 ASS 上。
  • 做不成时：内容为空、OCR 失败或门限没过的 srt 不放进成品，借走的 default 还给原轨。字幕复用第一次失败时，重试一律不带新增的 srt，只保住源自己的轨。

OCR 的开销与失败

图形轨的码流（.sup）是那次 demux 多出的一个输出，不额外读一遍源。demux 结束后才 OCR：tesseract 同时最多识别 16 条字幕，且不超过本容器的 CPU 预算。

读出来的文字要过一组结构门限（空条比例、时间轴、相邻条重叠、非 ASCII 字符、生词率等）。生产里没有标准答案可比，所以门限只查自洽，不声称准确度。下面任何一种都只降级成“这条轨没有 srt”并记一条告警，编码照常交付：没装 tesseract、.sup 解析不了、某条字幕的 tesseract 超过 60 秒、整条轨超过 900 秒、每条都读成空、门限没过，或任何意外异常。

不管开关怎么设，复用都会做的事

  • 音轨原样复制。字幕除 mp4 的 mov_text 外一律原样复制：mov_text 只存在于 mp4，Matroska 装不下，转成 srt；PGS、VobSub 这类图形字幕和 ASS 从不转换。
  • 每条音轨和保留下来的字幕都按源写上自己的 disposition 标记（default、forced、hearing_impaired 等），不让 ffmpeg 自己推断。它的推断是：同类的流不止一条、又都不是 default 时，把第一条标成 default。17 个 Stranger Things 输出就这样把一条空 PGS 轨标成了 default，Plex 选中它烧进画面。
  • 音轨和字幕的语言 tag 原样带过去。
  • 附件一起带过去，主要是 ASS 字幕排版用的字体；少了它，播放器会换用自己的字体，中日韩文字可能显示成方块。Matroska 源的附件由 mkvmerge 直接从源里整份拷贝，图片附件和 UID 都保留。带附件的那一步失败就去掉附件重试：丢一个字体只坏一条有样式的字幕，丢了复用就丢了整个编码。
  • 读不出源有哪些流时，保留全部字幕，只清掉字幕的 default 标记，其余标记照源复制；这种情况下不丢轨、不加 srt。
  • 最终封装用 mkvmerge，它不可用或失败时退回 ffmpeg；两条路写出的字幕标记一致，但 ffmpeg 这条路保不住图片附件和附件的 UID。

在哪看结果

这几件事记在应用日志里（进程的标准错误输出；logging.file 为 true 时也写进 dirs.logs 下的 av1transcode.log），不在队列页的作业日志里：丢了哪些空轨是一行 optimizer: dropping … empty subtitle stream(s)；每条 OCR 成功的轨一行 optimizer: OCR'd s:…，带条数、用时和门限用到的数字；没做成的是 no text copy of s:… 加原因，没装 tesseract 时是 pgs_ocr_srt is on but tesseract is not installed。成品的结构检查按源的字幕轨数减去丢掉的空轨、加上新增的 srt 来核对字幕数，所以丢轨、加轨都不会让它报错（见结构检查）。

Dolby Vision / HDR

P5（ICtCp）

libplacebo（Vulkan）转 HDR10 BT.2020+PQ。它是 ffmpeg 里唯一能应用 RPU 的滤镜，没有备用方案（旧的 zscale 已退役）。

优化器引擎逐镜头转换，无损分片放进 p5_cache_dir（默认 tmpfs，不落盘）；av1an 引擎要先把整片转成无损 FFV1 中间文件放进 dirs.work，45 分钟的 4K 一集约 100GB。用哪块 Vulkan 设备见 GPU 章的 Dolby Vision P5 转换。

P7 / P8

解码器直接返回基底层、自行忽略 EL/RPU，和旧的 dovi_split=bl remux 逐帧一致；那一步已删除（每集 4K 省约三分钟和一次 27GB 写）。RPU 单独保存为 .rpu。

成品按基底层本来的信号标记，以 DV 配置里的兼容 id（dv_bl_signal_compatibility_id）为准：1、6（8.1、7）是 HDR10，4（8.4，手机和广播常见）是 HLG，2（8.2）是 SDR。没有这个 id 时看视频流自己的传输特性，都没有时按 HDR10。

HDR10 / HLG

编码完用 mkvpropedit 在 mkv 视频轨上写色彩标签（AV1 码流头默认按 BT.709，不写播放器会显示错色）。HDR10 另写 mastering display / CLL：取源里的，源里没有就用 default_master_display / default_max_cll。HLG 只写 BT.2020 + HLG 标签，不写 mastering display / CLL。Dolby Vision 源：P5 转成了 HDR10，按 HDR10 标；P7/P8 按基底层标（见 P7 / P8），SDR 基底层和普通 SDR 源一样不写。整步由 hdr.preserve 控制。

成品校验

编码完成后成品要过两道检查，性质不同：结构检查两种引擎都做、不能关，不过就判作业失败；抽验镜头只有 optimizer 引擎做，只报告，不会让作业失败。顺序是拼接复用 → 抽验镜头 → 结构检查 → 作业标记完成；开了 delete_source 的话，源文件在标记完成之后才删。

verify_shots

默认 10

编码后抽验多少个镜头的实际交付质量；0 = 不验。这是全流程唯一的对账机制：它把“探测预测”和“实际交付”的偏差报出来，偏差大通常意味着窗口没对齐而不是编码器问题。代价是每个抽中的镜头再打一次分，逐个串行跑：生产机上一段 150 秒的 DV P8 片段（22 个镜头、GPU 打分）实测抽验 10 个镜头 43.6s，整个作业 398.5s。

probe_dataset.jsonl 里有什么

  • 作业开始一行 "type":"job"：文件名、分辨率、帧率、时长、目标、探测网格、探测编码器等。
  • 每探测完一个镜头一行 "type":"shot"：镜头位置与长度、探测窗口、探到的 (crf, 分数) 点，显卡也探过时的 (q, 分数) 点，以及交点。probe_encoder 为 qsv 时，只有标定被拒、整个作业退回 SVT 探测，才会写这种行。

  • 每行都带作业日志名 job（job_<id>，id 就是队列页的作业 id）和写入时间 t。

抽验镜头做了什么

CRF 是从快速 preset、最多 probe_max_frames 帧的探测编码里挑出来、再套到正式编码上的，此前没有任何一步核对成品是否真落在探测说的位置。抽验补的就是这一步：

  • 抽哪些：沿时间轴均匀铺开抽 verify_shots 个镜头，含第一个和最后一个；只抽 1 个时取中间那个。不随机抽，是因为值得抓的毛病是位置性的：定位从某处开始错、镜头表提前用完，都会让那一点之后的镜头全部偏低，均匀抽样看得出这道断崖。
  • 比什么：每个镜头取它探测时的那段窗口，把成品里这一段和源的同一段帧用 target_metric 打分，再和探测曲线在所选 CRF 处预测的分数比。两边直接读、不落中间文件；SSIMULACRA2 和 Dolby Vision P5 源例外，要先把两边窗口各抽成一个 FFV1 无损文件。打分线程：预设或优化器设置里写了 vmaf_threads 就用它，否则取本容器可用核数的一半（见 vmaf_threads）。
  • 在哪看：队列页显示「成品质量校验中」，进度是「校验 已完成/总数 段」。作业日志（队列页「日志」）里每个镜头一行 verify shot … crf … predicted=… delivered=…，最后汇总交付分数的最低、中位、最高和目标，以及（有预测值时）“探测预测 vs 实际交付”的平均偏差。有镜头低于目标、交付平均比预测低 5 以上（差这么多通常是两边窗口装的不是同一批帧，而不是编码器差异）、或平均偏差达到 0.5（这时提示可以用 probe_crf_offset 把偏差换回体积）时，应用日志里另有一条。作业日志超过 logging.retention_days（默认 7 天）会被删掉。
  • 不会让作业失败：某个镜头打不了分就跳过并记告警；一个都打不了，只记一条 no shot could be verified。
  • 看不见什么：两边窗口用同一套定位去找，定位本身错了，两边会一起错开，分数照样对得上。

什么时候看它：动了 probe_max_frames 就得连着看这个偏差，只看快了多少会亏掉画质；probe_crf_offset 该填多少，看的也是它。

结构检查

两种引擎都做，不能关。只读成品的容器头（一次 ffprobe，不扫整个文件），和源比三样：时长相差不超过 1 秒或源时长的 0.5%（取大者）；音轨数相同；字幕轨数等于源的字幕轨数减去丢掉的空轨、加上新增的 srt（见字幕处理）。成品不存在或为空、读不出来、没有视频流，也算不过。不过就删掉成品，作业报错失败（结构不符时错误以 output verification failed for 开头），按 workers.max_retries 重试。开了 delete_source 时，这是删源之前的最后一道关：截断的编码、丢了音轨的复用都在这里拦下。

作业阶段与状态词表

队列页上每个作业都有两个词：状态（status，作业在队列里处于哪一步）和阶段（stage，引擎正在做什么）。下面每条先写界面上的字，后面的英文是 API、数据库和日志用的键；展开作业后「原始键」一行显示的就是这两个英文键。

progress 是每阶段重置的，不是整个作业的。每换一个阶段，百分比都从 0 重新算：优化器作业依次走分镜、探测、编码，开了抽验再走一遍校验，百分比会涨满、归零好几次。整个作业走到哪了，看阶段条。

状态

排队 pending

等空闲的 worker。worker 按提交时间从早到晚取，最早提交的先跑。刚提交的作业、失败后等重试的作业（阶段是准备重试）、服务重启时被打断的作业，都在这个状态。

排队中的作业一取消就变成已取消，不会再被取走。

分析中 analyzing

worker 已经领走这个作业，正在用 ffprobe 读源文件（分辨率、编码、HDR、杜比视界、音轨和字幕），然后决定跳过还是开始转码。

这时点「取消」或「取消全部排队」，作业立刻变成已取消；worker 分析完发现状态已经变了，不会再开始转码。

转码中 running

分析通过，引擎在跑。进入这个状态的那一刻记下开始时间（started_at）和源文件大小（size_before）；阶段先是一段准备中，然后是分镜、探测、编码，优化器开了抽验还有校验。

取消转码中的作业：阶段先变成取消中，引擎在下一次检查时停下，然后才变成已取消；成品如果已经写出，会被删除。

已完成 done

成品已写出并通过了结构检查（见成品校验），output_path、size_after 在这时写入，progress 记为 100。开了「删除源文件」的话，源文件在这之后才删。

重试后才成功的作业，错误里还留着上一次失败的原因：后端标记完成时不清空 error。队列页把它显示成灰色小字，不是红字。

失败 failed

重试次数用完了：失败后会自动重试，最多 workers.max_retries 次（默认 2），之后再失败才停在这里。error 是最后一次的原因，经过见作业日志。成品没通过结构检查时，那个文件已经被删掉，不会留在源文件旁边。

已取消 cancelled

被手动取消。排队中的作业立刻变成这个状态；转码中的作业要等引擎停下，期间阶段是取消中。成品如果已经写出，会被删除。

已跳过 skipped

分析后决定不转码。原因写在 error 里，队列页展开后显示为「跳过原因」，只有三种：

  • no video stream：源里没有视频流。
  • already AV1 (宽x高)：源已经是 AV1，开着 skip_existing_av1，并且高度不低于 transcode.min_height_to_transcode。
  • engine=optimizer requires target_quality (e.g. 75 or 75-85)：选了优化器引擎，却没有 target_quality。

阶段

阶段词有全称和简称两种写法。全称用在表格的「阶段与进度」列和「正在转码」区块；简称用在阶段条每一段的名字和手机卡片上。

场景检测 scenedetect

简称「分镜」

找切点。计数是已扫描帧数 / 总帧数，显示为「场景检测 N/M 帧」。av1an 引擎在它自己打出 Scene detection 时进入这一步，计数取自它的进度条。

质量探测中 probing

简称「探测」

用不同 CRF 试编码、打分，给每一段挑 CRF。优化器上计数是已探测镜头数 / 镜头总数，显示为「探测 N/M 段」。av1an 只有设了 target_quality 才真的探测，计数是已探测的分块数，这一步的百分比最多到 99。

转码中 encoding

简称「编码」

正式编码。全称和转码中状态是同一个词。优化器上计数是已编完镜头的帧数 / 总帧数，fps 是这一阶段开始以来的平均速度；到 100% 之后还要把镜头拼起来、封装音轨和字幕，这段时间百分比停在 100。av1an 上帧数和 fps 取自它自己的进度条。

作业一变成转码中，后端就先把阶段写成 encoding，引擎真正开始前的那一段界面显示为准备中。

成品质量校验中 verifying

简称「校验」

仅优化器：从写好的成品里沿时间轴均匀抽 verify_shots 个镜头（默认 10）重新打分，和探测时的预测对账，结果写进作业日志，显示为「校验 N/M 段」。它只报告，不会让作业失败。verify_shots 为 0 时没有这一步，阶段条上的「校验」一直不亮。详见成品校验。

分析中 analyzing

简称「分析」

与分析中状态同时出现。它不是阶段条上的一段：两种引擎的阶段条都从分镜开始，分析时一段都不亮，状态标记已经写着分析中。

取消中… cancelling

简称「取消」

已经请求取消一个转码中的作业，等引擎在下一次检查时停下；取消来自网页、API 还是命令行都一样。引擎换阶段时不会把它改掉。这时「取消」按钮不再显示，阶段条上不亮任何一段。

准备重试 retry

上一次尝试失败，作业回到排队，等再跑一次。队列页写成「准备重试（第 N 次）」，N 是 retries。见重试 N 次。

done / failed / skipped / cancelled

作业结束时和同名状态一起写入，队列页只显示状态。

空 ""

worker 刚领走作业、分析还没开始的一瞬间，以及服务重启后被放回排队的作业。界面这时显示状态词。

队列页上的其他词

阶段条

「正在转码」区块和每一行里的分段条。段数由引擎决定：

  • 优化器（engine=optimizer）：分镜 · 探测 · 编码 · 校验
  • av1an，设了 target_quality：分镜 · 探测 · 编码
  • av1an，没设 target_quality：分镜 · 编码

每段的长短只是大致比例，不是时间预测。走完的段保持填满，正在走的段按本阶段的百分比填，还没走到的只有一条细线。分析中和取消中都不是其中一段，这时不亮任何一段。表格行和手机卡片里的是不带段名的小号阶段条。

准备中

作业刚变成转码中、引擎还没报出第一个阶段时显示。后端在作业转为转码中的那一刻就把阶段写成 encoding，而引擎开始之前还有准备工作：杜比视界源开了 save_rpu 时要先把 RPU 从整个源文件里抽出来；av1an 引擎处理 P5 源时要先把整片转成 HDR10。大文件这一步可能要几分钟。

页面的判断：阶段是 encoding，百分比和帧数计数都是 0，并且这个页面没见过它经过更早的阶段。这时要是照字面点亮「编码」，会把分镜和探测画成已完成，接着又跳回分镜。

队列第 N 位

排队中的作业还要等几个：第 1 位就是下一个开始的。顺序就是后端取作业的顺序，提交时间最早的先跑。只有所有排队中的作业都已载入列表时才显示；列表被截断时显示「–」，因为这时算出来的数不可信。手机卡片上写成「第 N 位」。

重试的作业保留原来的提交时间，所以重新排队后通常排在最前面。

重试 N 次

一次尝试失败后，作业回到排队，阶段是准备重试，retries 加 1，error 记下这次的原因（队列页用红字显示）。workers.max_retries（默认 2）是自动重试的上限，所以一个作业最多跑 1 + max_retries 次；retries 已经等于 max_retries 的作业正在最后一次尝试，再失败就停在失败。

界面只写「重试 N 次」，不写「N/2」：max_retries 不在任何 API 返回里，照抄 config.yaml 的默认值，哪天改了配置就会说错。

每次重试都从头开始：新的工作目录，分镜、探测全部重跑，没有断点续跑。服务重启时正在跑的作业也回到排队、从头开始，但不算一次重试（retries 不变）。

等待 / 已跑 / 用时

展开作业后的几个时长。等待（排队中写作「已等待」）是从提交到开始转码，分析也算在里面；已跑（进行中）和用时（已结束）是从开始转码到现在或到结束。

「开始转码」指分析通过、状态变成转码中的那一刻（started_at）。它在每次重试和服务重启时清空重记，所以已跑、用时只算最后一次尝试，前面失败的尝试都落进了等待。

剩余

「正在转码」区块里百分比旁边的剩余时间。只在编码阶段、并且已有帧数和 fps 时显示，算法是（总帧数 − 已编帧数）÷ fps。它是编码这一阶段还剩多久，不是整个作业：优化器编完之后的拼接封装和校验都不算在内；分镜、探测、校验阶段不显示剩余。

优化器的帧数只在一个镜头整段编完时才增加，所以第一个镜头编完之前没有剩余时间。超过一小时显示为 时:分:秒。

源 → 成品

源文件大小 → 成品大小，后面的百分比是成品比源小了多少：↘N% 是小了 N%，↗N% 是成品反而比源大了 N%，±0% 是差不多一样大。转码开始前源的大小取自分析结果。成品比源还大时，先看 min_crf 那一条讲的机制。

顶栏状态行

队列页顶栏的一行字，页面每 4 秒问一次后端：

  • 「转码中 N · 分析中 N · 排队 N」：各状态的作业数，分析中为 0 时不写；没有转码中的作业时开头是「worker 运行中」。桌面上后面还跟着上次刷新成功的时间，手机上省掉。
  • 「worker 停止」：/api/status 的 workers_running 为 false，队列没有在运行，排队的作业不会开始。
  • 「与服务端失去联系，N 秒后重试」：刷新失败。页面颜色变淡，同时弹出一条不会自动消失的提示，写明原因和数据停在几点；重试间隔按 4、8、16、32 秒拉长，连上后提示「已恢复连接」。

标签页在后台时页面不刷新，切回来立即刷新一次。

环境变量覆盖

config.yaml 里写出来的每一项都可通过环境变量覆盖（容器内优先于 config.yaml）：AV1TC_<段>_<键>，嵌套的段依次接上，例如：

AV1TC_TRANSCODE_PRESETS_BALANCED_CRF=26
AV1TC_WEB_PORT=9090
AV1TC_WATCHER_MIN_SIZE_MB=5

布尔值接受 1/true/yes/on，数字自动转换。别的写法的布尔值一律当 false；整数字段写的不是整数就忽略，保留 config.yaml 的值。列表写成逗号分隔，如 AV1TC_WATCHER_EXTENSIONS=mkv,mp4。键名本身带下划线没关系（如 AV1TC_DIRS_SETTINGS_FILE）：每一层取能对上的最长一段。

只认 config.yaml 里已经写出来的键：没写的（比如预设里没列的字段，或 transcode.video 的 target_quality）用环境变量设不上，也不报错；挂自己的 config.yaml 时同理。AV1TC_TRANSCODE_VIDEO_CRF 虽然对得上键，但 transcode.video 启动时会被默认预设的值替换，见上，所以改 CRF 要改预设。网页端存进 settings_file 的那几项（并行数、delete_source、优化器参数、vulkan_device）启动时再盖在环境变量之上。

CLI 用法

python3 -m app.cli run                    # 队列 + Web；watcher.enabled 时再加监视
python3 -m app.cli run --no-watch --no-web
python3 -m app.cli process <file> --single --custom crf=24 --custom preset=3
python3 -m app.cli process <file> -p compact
python3 -m app.cli scan                    # 把输入目录里没做过的文件入队
python3 -m app.cli scan --preset compact
python3 -m app.cli presets                 # 查看当前预设
python3 -m app.cli status / cancel [job_id] / check

每个命令都接受 -c/--config <路径>，不给就用程序根目录下的 config.yaml。镜像的入口就是 python3 -m app.cli，默认命令是 run；在容器里跑其他命令：docker exec av1transcode python3 -m app.cli status。

run

完整运行：队列 worker，加 Web（web.enabled）和监视（watcher.enabled）。--no-watch / --no-web 分别关掉监视和 Web，没有 Web 时前台常驻，Ctrl-C 退出。启动时先删掉上次被强杀的作业留在 dirs.work 的临时文件，再按 retention_days 清旧作业日志，并把库里停在 running / analyzing 的作业改回 pending 重新排队。

process <file>

提交一个文件；给目录则提交它第一层里扩展名匹配的文件。-p/--preset 选预设，--custom key=value 可重复（见自定义参数），-s/--single 在当前进程前台跑完。

不带 --single 只把作业写进任务库，由正在跑的 run 领走（它每 2 秒看一次库），不碰库里其他作业；同一个文件已在排队或转码时不重复提交。没有 run 在跑时，作业就一直排队。

scan

把 dirs.input 下（总是递归）扩展名匹配、且任务库里从没有过作业的文件入队，--preset 选预设。和监视器用同一套规则：跳过 av1/、work/、rpu/ 子目录；做过的文件（不论完成、失败、跳过还是取消）不再入队，要重新提交用 process。只写任务库，由 run 处理。不看 min_size_mb、不等文件稳定。

status

各状态的作业数，加最近 15 个作业（id 前 8 位、状态、进度、文件名）。

cancel [job_id]

不给 id 就取消所有排队中和分析中的作业。id 可以只写 status 列出的前 8 位。排队中、分析中的作业直接取消；正在编码的作业标成取消中，正在跑的服务在下一次检查时（一秒左右）停下。已结束的作业不会被改动，命令以状态码 1 退出。

presets

列出当前生效的预设（config.yaml 加 presets_file）：crf、preset、film_grain、passes，有 additional_video_params 的也列出。

check

逐个检查 tools 段的可执行文件在不在，缺一个就以退出码 1 结束。

API

所有接口都在 /api/ 下，收发 JSON（日志除外，是纯文本）；出错时返回 HTTP 错误码和 {"detail": …}。服务默认监听 0.0.0.0:8080（web.host / web.port）。默认那一行写着「需密钥」的接口，在设了 web.api_key 之后要带请求头 X-API-Key，见密钥。

密钥 X-API-Key

配置 web.api_key · 默认 空

web.api_key 为空时所有接口都开放。设了之后，下面这些接口要求请求头 X-API-Key 与它完全一致，缺了或不对都返回 401 {"detail": "invalid api key"}：所有写操作（提交、取消、清除历史、改预设，改并行、优化器（包括 DELETE /api/settings/optimizer）、GPU、删除源文件设置），GPU 自检（POST /api/gpu/selfcheck），以及 GET /api/browse。

其余的读接口不需要密钥：/api/health、/api/status、/api/jobs（含单个作业和日志）、/api/presets、/api/workers、/api/settings/optimizer（含 /defaults）、/api/gpu、/api/settings/safety，以及页面本身。

curl -H 'X-API-Key: 你的密钥' -X POST http://主机:8080/api/cancel

/api/health /status /jobs /presets /workers

方法 GET

状态、任务、预设、并行设置（开放读取）。

  • /api/health：{"status": "ok", "time": …}，只说明服务活着。
  • /api/status：jobs（七个状态各有几个作业）、queue_len（排队数）、workers_running（队列 worker 是否在跑）、dirs（全部目录配置，没配的目录是字符串 "None"），以及重复其中三个目录的 system。
  • /api/jobs?status=…&limit=…：按提交时间从新到旧。status 取七个状态之一，不给就是全部；limit 默认 100，最大 500，超过返回 422。每个作业的字段见单个作业。

  • /api/workers：concurrency、av1an_workers，以及 active_worker_count（当前实际的 worker 线程数；调小 concurrency 后，多出的 worker 做完手上的作业才退出）。

/api/jobs/{id}

方法 GET

单个作业，字段和列表里的一样；id 不存在返回 404。

字段：id、source、status、stage、progress（本阶段的百分比，见词表）、progress_done / progress_total / progress_fps（本阶段的计数和速度）、error、meta（分析结果：分辨率、帧率、编码、时长、音轨数、HDR、杜比视界）、params（提交时的 {source, preset, overrides}）、output_path、rpu_path、size_before / size_after（字节）、retries、created_at / started_at / finished_at（Unix 时间戳，秒）。

API 不返回逐镜头的数据（每个镜头选的 CRF、抽验分数），这些只在作业日志里。

/api/jobs/{id}/log

方法 GET

任务日志。

纯文本，就是 dirs.logs 下的 job_<id>.log。文件不存在时返回 404 {"detail": "no log"}：作业还没进入编码引擎；日志已超过 logging.retention_days（默认 7 天，按修改时间算，启动时和之后每 6 小时清一次）；或者被「清除历史记录」删掉了。重试时优化器接着往同一份日志里追加，av1an 引擎则从头重写。

/api/jobs

方法 POST · 需密钥

入队：{"path": "...", "preset": "balanced", "overrides": {"crf": 24}}。

返回 {"job_id": "…"}。path 必填，填容器里看得到的绝对路径。给目录时，目录里（不含子目录）每个扩展名在 watcher.extensions 里的文件各排一个作业，返回第一个的 id；给单个文件时不查扩展名。同一个源已经有排队中、分析中或转码中的作业时不新建，直接返回那个作业的 id。缺 path、路径不存在、目录里没有可识别的文件、overrides 不是对象，都返回 400。

preset 不填就用 transcode.default_preset（默认 balanced）；custom 以默认视频参数为基准（见自定义参数）；不存在的预设名在作业开始时回退到默认预设，日志里记一条警告。overrides 的键是预设参数名，不认识的键、值为 null 或空字符串的键都被忽略。

作业只记下预设的名字和 overrides，预设的具体参数到作业开始分析时才读：排队期间改了预设，还没开始的作业会用改后的值，重试时也会重新读。

/api/jobs/{id}/cancel

方法 POST · 需密钥

取消任务（需 api_key）。会中断在编的任务并删除其输出文件。

返回 {"cancelled": "<id>"}，id 不存在返回 404。排队中的作业立刻变成已取消；转码中的作业先变成取消中，引擎在下一次检查时停下，然后才是已取消。

分析中的作业也立刻变成已取消，worker 分析完发现后不会开始转码（见分析中）。已结束的作业（已完成、失败、已跳过、已取消）不会被改动，返回 409。队列页只给排队中、分析中、转码中的作业显示「取消」。

/api/cancel

方法 POST · 需密钥

把所有排队中和分析中的作业标成已取消，返回 {"cancelled": 数量}。转码中的作业不受影响，要停它用上面的单个取消。队列页的「取消全部排队」就是它。

阶段记为已取消并写入结束时间。分析中的那几个，worker 分析完会发现并停下，不会开始转码。

/api/jobs/prune

方法 POST · 需密钥

删除已结束作业的记录，返回 {"pruned": 删掉的记录数, "logs_removed": 删掉的日志数}。请求体可选，{"statuses": ["failed", "cancelled"]} 表示只删这几种；只认 done、failed、skipped、cancelled，其他值被忽略，不给就四种全删。排队中、分析中、转码中的作业不会被删。

删完记录，dirs.logs 里所有对不上现存作业的 job_*.log 都会被删掉，包括早就没有记录的孤儿日志；就算这次一条记录也没删，照样清。队列页的「清除历史记录」就是不带 statuses 的这个调用。

开着 watcher 时注意：watcher 靠作业记录判断一个文件处理过没有。记录被删掉的文件如果还在输入目录里，服务重启后会被当成新文件再排一次。

/api/gpu/selfcheck

方法 POST · 需密钥

优化器自己的 SYCL 预检：同一对测试画面在 GPU 上和 CPU 上各打一次 VMAF，再比较。请求体可选 {"device": N}，默认用 vmaf_sycl_device，负数按 0。

FastAPI 另外自动提供 /docs（Swagger UI）、/redoc 和 /openapi.json，列的就是上面这些接口；前两个的脚本从 cdn.jsdelivr.net 加载，浏览器上不了外网时打不开。

网页端如何带密钥

密钥是服务端配置，页面没法从服务端读到它。在「设置 → API 密钥」里填一次，存在这个浏览器的 localStorage 里（键名 av1tc_api_key），之后队列页和设置页的每个 /api 请求都自动带上 X-API-Key，读请求也带：哪些接口要密钥由服务端决定，页面不用跟着改。

收到 401 时页面会说清原因：没存密钥时提示「此操作需要 API 密钥（401）」，存了但对不上时提示「API 密钥被拒绝（401）」，两种都指向「设置 → API 密钥」。换浏览器或清掉站点数据后要重新填；隐私模式下可能存不住。
